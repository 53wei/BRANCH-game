# 《游园惊梦：四面证词》重构 Source of Truth

Updated: 2026-09-02

## 1. 固定优先级

后续任何实现、修复、文案、UI、关卡、CG、证物和任务接入，按以下优先级执行：

1. **剧情事实**：工作区根目录 `游园惊梦_完整剧情母剧本_V5.0.md`
2. **整体设计 / 玩家体验解决方案**：工作区根目录 `游园惊梦_整体重构执行母文档_V1.0.md`
3. **工程实施顺序与验收**：工作区根目录 `游园惊梦_重构TASK执行计划_V1.0.md`
4. **当前 Runtime 与旧代码**：只能作为现状证据，不能反向覆盖前三项。

若新剧本与旧 Ink / hardcoded StoryLine / bark / UI string 冲突，以剧情母稿为准。

若 TASK 与母文档出现无法解释的直接冲突，停止该冲突项并记录到 `open-questions`；不得现场猜剧情或自行折中。

## 2. 当前执行模式：严格顺序闭环

执行纪律以 `EXECUTION_PROTOCOL.md` 为准。**必须从当前尚未闭环的最前 TASK 开始，禁止跳 TASK、跳步骤、跳剧情场景或跳原始问题。**

仓库里已经存在的重构实现只能降低重复劳动，不能改变执行顺序：到达某个 TASK 后仍需重新完成“完整提取 → 当前实现核查 → 制作/补齐 → 回母文档反查 → 验证 → 关闭判断”。

每个 TASK 使用以下状态：

- `DONE`：工程交付、Runtime 绑定、旧实现清理和当前环境可执行的验证均满足 TASK；
- `DONE / VERIFY-DEFERRED`：工程交付满足，但明确的设备/浏览器/本机环境阻塞使某项运行验证只能延后；必须记录原始阻塞并在发布 QA 前补验；
- `PARTIAL`：已有正确实现，但仍有可在当前环境继续完成的工程缺口；
- `TODO`：尚未形成满足任务目标的有效实现。

执行原则：

> 已有正确实现保留；错误或冲突实现清理；缺失项补齐；但绝不因为“以前已经做过一部分”越过该 TASK。

## 3. 开发与验证节奏

采用三层验证，不允许“每做一小步就验证半天”，也不允许“所有验证全部拖到最后”。

### A. 顺手验证

能低成本执行的检查立即执行：

- 类型检查；
- 单元测试；
- 静态搜索；
- 资源路径存在性；
- manifest / schema 一致性；
- 已有自动化回归。

若命令因 WSL、权限、额度、网络、工具缺失等环境问题无法执行，记录为 `VERIFY`，**不阻塞没有依赖的后续实现**。

### B. 阶段验证

一个完整功能包或章节改完后统一验证：

- 序章 / 第一章 walkthrough；
- 地图、碰撞、相机、存档；
- UI 截图与信息负荷；
- CG / 证物 / 案卷流程。

### C. 最终发布门禁

TASK-054～060 统一处理：盲测、全章节 QA、浏览器/设备、存档恢复、WebGPU/WebGL2、P0 问题关闭与证据归档。

## 4. 不允许的“完成”定义

以下情况一律不能单独算完成：

- “代码文件已经存在”；
- “资源已经下载到目录”；
- “测试文件写了但未证明 Runtime 调用”；
- “能编译”；
- “有一个新组件，但旧实现仍然覆盖它”；
- “只在 dev/debug route 生效”；
- “截图看起来差不多，但核心玩家流程未接入”。

最终完成仍以 Runtime 实际生效和 TASK-060 发布门禁为准。

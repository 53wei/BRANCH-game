# 0. 文档治理、版本优先级与防偏规则

## 0.1 为什么现在必须有 Master GDD

项目目前已经同时存在旧 V1 GDD、阶段性 V2 GDD、剧情母文档 V3、机制软件计划、建模计划、视觉计划、队友基于旧 GDD 的实现，以及 Codex 已经做出的场景/资产/逻辑。各自都有价值，但如果继续平行推进，会出现“文件名相同、代码名相同、产品含义不同”的语义冲突。

本 V4.0 的目的不是推翻过去，而是完成三件事：

- 统一产品事实。 明确什么是当前游戏、什么已经淘汰。

- 统一制作关系。 明确剧情、玩法、关卡、美术、建模、程序之间谁给谁输入。

- 统一团队执行。 队友和 Codex 在写代码前都能知道当前唯一目标，不再各自依据不同版本开发。

## 0.2 文档优先级

- 优先级： P0； 文档/信息： 本《Master GDD V4.0》； 规则： 项目最高 Source of Truth

- 优先级： P1； 文档/信息： 本文内嵌的 Narrative Source of Truth / Mechanics Spec； 规则： 用于剧情和机制细化，不得与主文冲突

- 优先级： P2； 文档/信息： 当前章节 CDD / Level Design / Art Brief； 规则： 只能决定“怎么表现、怎么实现”

- 优先级： P3； 文档/信息： 当前执行计划、Codex Task、资产计划； 规则： 服从 P0-P2

- 优先级： P4； 文档/信息： 仓库当前代码； 规则： 代码是实现现状，不自动等于设计真相

- 优先级： P5； 文档/信息： 旧 V1/V2 GDD、历史 Prompt、旧任务计划； 规则： 只作参考；冲突内容进入迁移/废弃表

## 0.3 决策状态

- [LOCKED 已锁定]：后续默认不得改变；如要改变必须先升级 Master GDD。

- [STAGED 阶段性]：当前可执行，但允许通过测试调整。

- [CANDIDATE 候选]：可研究，不进入正式制作主线。

- [UNRESOLVED 未决]：没有答案，禁止实现端擅自决定。

- [DEPRECATED 已淘汰]：历史设计，不继续开发；若有旧代码先迁移再清理。

## 0.4 最重要的防偏原则

- 剧情 Source of Truth 决定“发生了什么、玩家什么时候知道什么”。

- 玩法决定“玩家用什么动作得到这些信息”。

- 关卡决定“这些动作发生在哪里、如何形成 Thought Path”。

- Art Direction 决定“玩家最终应该看到什么、感到什么”。

- Modeling / Asset Production 负责提供三维形体和素材，不负责独立决定最终视觉。

- Environment Art 负责把模型、材质、道具、植被、构图、灯光组织成最终场景。

- 程序负责规则、状态、交互、渲染与性能，不得用程序低模替代已经验证的正式视觉资产。

- 成熟通用问题优先复用成熟库；只把开发资源花在《游园惊梦》独有的认知重构上。

## 1.2 一句话产品描述

玩家回到一座自己曾经生活过的江南园林调查一桩旧案。四个人对同一地点拥有互相矛盾、各自完整却都不可靠的认知版本。玩家不是简单“找不同”或在菜单里选谁可信，而是切换、窥视、借出、锚定并组合这些认知差异，让原本不可能成立的空间暂时成立，以此取得案件事实；最终发现被所有人从现实中删除的第五个人正是自己，并亲手重构出属于自己的“第五种听雨轩”。案件核心事实会收束，但玩家保留、使用和最终组合的认知不同，会形成不同的终局现实与结局表达。

## 1.3 核心命题

如果记忆、感知和别人的证词都能构成不同版本的现实，你凭什么确定自己经历过的那个版本才是真的？

玩家向短句：你相信自己看到的吗？

## 1.4 核心体验支柱

### 支柱 A：空间是证词

证词不是文本菜单，而是可走、可验证、可操作的空间状态。

### 支柱 B：异常是工具

玩家不是只发现“哪里不一样”，而是把差异拿来解决问题：借桥、借廊、借门状态、锚定并跨认知保留。

### 支柱 C：推理由玩家完成

系统提供事实，不宣布“谁撒谎”“哪个是真相”。反转来自旧证据获得新解释。

### 支柱 D：真实空间先成立

听雨轩必须先是一座让玩家能记住、能相信、能形成方向感的真实园林；只有这样，门消失、路循环、尺寸不成立才有力量。

### 支柱 E：恐怖来自认知失稳

不是满屏血、鬼脸、红灯和随机 Jumpscare，而是：熟悉的门不再存在、走过的路回到原点、框景里出现另一个现实、最终连自己的记忆都不可靠。

### 支柱 F：所有认知都不可靠，包括玩家

四名在场者不是“错误答案”，玩家也不是上帝视角。每个人的认知都由记忆、感知、误解、自我保护和事后补全共同构成。终局不能变成“终于找到唯一客观视角”，而应变成：玩家掌握了足够的事件事实，却仍必须亲手决定哪些认知碎片值得保留、如何让它们共同成立。

### 支柱 G：结局由重构行为产生，不由 Trust UI 产生

旧版“选择相信谁→世界按谁重构”的创意保留其结果层价值，但废弃菜单式 Trust Node。当前版本把结局分歧转移到玩家实际行为：探索了哪些可选证据、使用了哪些认知解法、锚定过哪些认知组件、终局最终保留了哪些互相冲突的碎片。系统不问“你信谁”，而让玩家通过操作留下自己的第五份证词。

## 1.5 Demo 体验基准

5 秒看见变化，30 秒懂“有意思”，5 分钟开始问“那我是不是还能……？”

核心机制成功的表现，不是玩家背会术语，而是自然提出：

- “能不能把那座桥带到另一个版本？”

- “这个门框里面为什么不是同一个地方？”

- “我锚定以后再切换，它是不是还在？”

- “如果两个人都只记得一部分，我能不能拼出第三种路线？”

## 1.6 明确不是哪种游戏

- 不是 3D 找不同。

- 不是“F 标记矛盾 + 系统判真假”。

- 不是“信任谁”UI 决定世界真相；但玩家实际采用和保留的认知会影响最终重构与结局版本。

- 不是传统四嫌疑人找唯一凶手。

- 不是 Walking Simulator。

- 不是纯密码锁合集。

- 不是完整时间旅行游戏。

- 不是四个人各拥有一套超能力。

- 不是依赖大量 Jump Scare 的恐怖游戏。

- 不是只有一个被系统标为“真结局 / True Ending”的线性终局。

## 1.7 商业与市场历史假设

旧 V1 曾提出网页首发、后续 Steam/Epic、$14.99 / ¥78、首年 5–10 万份等商业假设。这些数据目前不视为锁定结论，仅保留为历史参考。正式定价、发行、销量目标必须在 Vertical Slice 质量、游戏时长和平台策略重新评估后单独确认。

# 2. 玩家操作、核心循环与解谜原则

## 2.1 玩家核心动词

当前核心动词不是旧版的“走 / 切 / 信”，而是：

- 走 / Explore：形成空间记忆、验证路径与地标。

- 看 / Inspect：第一人称调查证据、门缝、窗框、脚印、画像、记录。

- 切 / Shift：主动切换认知版本。

- 窥 / View：通过月洞门、漏窗等看另一认知局部。

- 借 / Borrow：把另一认知中的可用空间组件或状态带入当前世界。

- 锚 / Anchor：让借来的东西跨认知继续存在。

- 组 / Reconstruct：后期组合多个认知组件，形成任何单一角色都没有完整记住的空间。

- 推 / Infer：玩家自己根据事实形成结论。

## 2.2 当前核心循环

进入一个熟悉/可理解的空间
→ 发现无法解释的事实或阻碍
→ 形成假设
→ 调查 / 切换认知验证
→ 通过 Borrowed View 发现另一版本的可用条件
→ Borrow / Anchor / 组合
→ 世界发生明显、可利用的变化
→ 到达新区域或获得新证据
→ 玩家更新自己的案件模型
→ 产生更大的问题

## 2.3 谜题结构标准

所有重要谜题尽量遵循：

发现 / Question
→ 假设 / Hypothesis
→ 尝试 / Experiment
→ 顿悟 / Insight
→ 新信息 / Evidence

禁止把“找钥匙→开门”当成核心谜题；钥匙、门闩、文档可以存在，但必须服务调查和认知。

## 2.4 五条白板规则

- 解谜要有顿悟。

- 解谜本身推进调查。

- 玩家自己得出结论。

- 核心操作必须造成明显世界变化。

- 不做纯找东西、纯开锁、纯跑图。

## 2.5 多解原则

第一版不追求无限 Sandbox，但至少保留“系统允许组合”的设计空间。典型谜题：

- A：桥完整，门关闭。

- B：桥断裂，门打开。

- C：没有桥，但有倒下的梯子。

可能解：

- 借 A 的桥并锚定，切 B，跨桥利用打开的门。

- 借 C 的梯子，从侧路进入。

如果所有 Puzzle 最终都只有设计者规定的一条 Scripted Sequence，认知重构就没有形成系统性。

# 3. 详细游戏机制与软件实现总规范

本章给出当前正式的软件映射。技术名称不是产品真相；如果仓库已有质量更高的等效实现，优先复用现有，不为符合文档名字而重写。

## 3.1 复用优先矩阵

- 问题： 渲染； 优先实现： Three.js WebGPURenderer； 原则： 保持当前引擎

- 问题： 第三/第一人称相机； 优先实现： camera-controls 或仓库同等级成熟实现； 原则： 不重写完整相机插值引擎

- 问题： 玩家移动； 优先实现： Rapier Kinematic Character Controller； 原则： 通用 move-and-slide 直接复用

- 问题： 相机防穿； 优先实现： Rapier ray/shape cast； 原则： 不堆大量手写射线

- 问题： 借景 Portal； 优先实现： Three.js 官方 WebGPU Portal / render pass 思路； 原则： 先抄成熟母体

- 问题： 调查拾取； 优先实现： Three.js Raycaster； 原则： 只检测 Interactable layer

- 问题： 角色动画； 优先实现： Mixamo + AnimationMixer； 原则： 做薄状态机

- 问题： 空间音频； 优先实现： Three.js AudioListener / PositionalAudio + Web Audio； 原则： 不重造 Audio Engine

- 问题： GLB / KTX2 / Meshopt； 优先实现： 当前 RuntimeAssetLoader 管线； 原则： 已完成则禁止重做

- 问题： 自动浏览器验证； 优先实现： 现有 Playwright/E2E； 原则： 没有才补最小方案

## 3.2 世界状态结构

不要创建四张完整复制地图和四个物理世界。采用：

TingYuXuanWorld
├── sharedWorld
├── cognition/protagonist
├── cognition/wife
├── cognition/gardener
├── cognition/accountant
├── cognition/artist
├── borrowedLayer
├── anchoredLayer
├── interactionLayer
├── gameplaySkeleton
└── proceduralDressing

认知对象使用数据状态控制 visible / transform / material / collision / interaction / light / audio。

## 3.3 第三人称主探索 + 第一人称调查

第三人称承担园林移动、空间记忆、跟随 NPC、地标阅读、远景目标。
第一人称 InvestigationMode用于脚印、门缝、漏窗、月洞门、文档、画像、近距离证据和强空间谜题。

过渡目标：200–450ms；退出后恢复原方向；不硬切；不允许切换绕过碰撞；第一人称隐藏会穿镜头的头/上身，但动画不重置。

## 3.4 Cognition Switch

切换不是全屏换滤镜。它必须同步：

- 场景可见对象；

- 门、墙、道路、道具状态；

- collider；

- interactable；

- 灯光；

- 环境音；

- puzzle hook。

关闭所有粒子与后处理后，玩家仍然应该一眼看出空间真的变了。

## 3.5 Borrowed View / 借景

月洞门、漏窗、屏风或特定框景可以实时显示同一坐标下另一个 Cognition 的局部空间。

第一版优先复用 Three.js webgpu_portal / WebGPU render pass 母体：主视角位置基本相同，PortalSurface 只渲染目标 Cognition Group。由于认知版本共用世界坐标，不需要第一天就实现通用 Portal A↔B 任意坐标变换。

限制：同屏 1–2 个 active portal；远离/完全遮挡暂停；不递归 portal；独立 portal resolution。

## 3.6 Loop Space / 假山回环

第一版采用：遮挡 + Rapier Sensor + paired transform teleport。

玩家进入假山/转角遮挡段后映射到出口，保留 yaw、移动意图和连续环境音。优先通过空间构图隐藏传送；只有穿帮才逐级升级为 camera continuity / portal teleport。

成功标准：首测玩家自然说“我怎么又回来了？”，而不是“刚才被传送了”。

## 3.7 Borrow / 借出

第一版只支持白名单：StoneSlab / BridgeSegment / CorridorSegment / DoorState。

Borrow 不是复制整张 Scene，而是在 borrowedLayer 生成或启用预制 runtime instance，并启用对应 Rapier collider。玩家必须能真实站立、通行、开门，而不是看到一张幻影贴纸。

## 3.8 Anchor / 锚定

第一版只做 1 个 Anchor Slot。未锚定 Borrowed Object 随认知切换恢复；锚定后跨认知继续存在。必须支持解除、Puzzle reset、安全 checkpoint 与 Softlock recovery。

核心验收：

A 认知看到桥
→ Borrow
→ Anchor
→ Switch B
→ 桥仍在
→ 玩家真实走过

## 3.9 Evidence / 证据系统

系统保存事实，不保存“谁撒谎 +1”。重大结论至少有三个独立通道：空间 / 物体 / 文字图像人物。

证据事实保持不变，后期变化的是 interpretation。例如“离家记录”：前期证明主角已离开；中期显示有修改痕迹；后期重新解释为给主角制造不在场证明。

## 3.10 Narrative Gate / 半开放调查

章节内部允许不同顺序、不同路线、漏掉个别证据；关键认知跃迁保持顺序：

认知不同
→ 第五人存在
→ 第五人 = 玩家
→ 删除 = 保护
→ 事故 + 延误救治

Gate 使用“requiredAll / requiredAny / minimum evidence channels”，不要在代码中散落大量 if(foundA && foundB)。

## 3.11 Reconstruction Trace / 认知重构轨迹与结局系统

旧 V1 最有价值的思想之一是“不同认知最终会导向不同结局”。当前版本恢复这个结果，但不恢复 Trust Score / Trust Node。

系统不保存“玩家相信夫人 +2”之类的隐藏道德分，而保存玩家真正做过的重构行为：

interface ReconstructionTrace {
discoveredOptionalEvidence: string[];
solvedWithCognition: Record<string, string[]>;
anchoredFragments: string[];
preservedContradictions: string[];
finalAssemblyFragments: string[];
}

规则：

- 案件硬事实不分支。 主角回来过、沈老爷摔伤、主角没有推人、四人共同删除主角痕迹、保护行动延误救治，这些不能被结局改写。

- 认知解释与最终现实分支。 玩家一路更常使用、主动保留和最终组合的认知，会改变《第五种听雨轩》的空间组织、可见证据、声音、最后注视的物件和结尾文本。

- 不能由隐藏分数单独锁死结局。 早期行为只影响终局可用碎片、推荐/默认摆位和微变体；最后一次 Fifth Reconstruction 必须给玩家真实操作空间。

- 不设置“正确结局 / 坏结局”。 不同结局是同一组事实在不同认知结构中的终局版本。

- 重玩价值来自重新构造，而不是刷四周目解锁真相。 章节选择/二周目可以让玩家发现不同可选证据和替代解，从而构成不同终局。

### 结局家族（Production Target）

所有结局都属于《第五种听雨轩》的不同重构版本，不是四个人各自的“真相路线”：

- A 家宅重构 / Domestic Lens： 沈夫人相关生活痕迹、房间、物品保存占主导。终局更强调“家人为了让你离开而把你从家中抹掉”的矛盾；空间更像真实住过的家。

- B 路径重构 / Spatial Lens： 老周相关侧路、封路、行动路线占主导。终局拥有最清楚的物理行动链；外部尺寸余刺会更直接刺穿“我已经拼对了”的确定感。

- C 文书重构 / Documentary Lens： 钱先生的账册、时间、车票、建筑记录占主导。被写下的区域极稳定，未被记录的旧房和侧路更容易出现轻微不稳定；结尾强调“记录能证明事实，也能制造事实”。

- D 图像重构 / Pictorial Lens： 柳生的画、视角、人影、框景占主导。终局更多依赖观看位置成立；结尾强调“我看见的，是当晚发生过的，还是后来被画进记忆的？”

- E 复合重构 / Composite Fifth Testimony： 玩家主动保留多份彼此冲突的认知，不让任何单一视角占主导。多个互相矛盾却可用的空间条件共存。它不是 True Ending，只是最明显承认“第五现实本身也是第五份证词”的版本。

允许 A+B、C+D 等混合微变体，但制作阶段先保证五个家族可读，不无限组合爆炸。

## 3.12 View-dependent Evidence

柳生相关证据可通过 camera position zone + view direction + angle tolerance + Raycaster occlusion 实现。玩家从特定月洞门/窗框角度看到人影，离开角度后不成立。

## 3.13 认知差异不是四套超能力

- 沈夫人：家庭生活与物件状态 → CognitionState + Prop Variant。

- 老周：路线与封路 → CognitionState + Collider + LoopLink。

- 钱先生：记录与“被记录才稳定”的结构 → Document/Evidence + Object visibility。

- 柳生：图像与观看角度 → ViewCondition + Portal/Visibility。

不开发“钱先生文字魔法”“柳生时间超能力”“园丁重力超能力”等独立引擎。

## 3.14 后期机制扩展

- 第三章“不存在的房间”复用 Borrow + Anchor + CognitionState + PuzzleDefinition。

- 第五章雨夜用 Scripted Reconstruction State / EventTrack，不变成完整时间旅行。

- 终章 Fifth Reconstruction 复用 anchoredLayer + multiple borrowed components，并读取 ReconstructionTrace 形成不同重构结局版本。

- Cognition Echo / 行为重演保留候选，不在核心 Vertical Slice 开发。

# 4. 剧情 Narrative Source of Truth（完整锁定版）

以下内容直接作为当前剧情真相与信息揭示顺序，不得被美术、关卡或程序自行改写。

用途：剧情真相、信息揭示顺序、角色认知与章节叙事的唯一基线。
状态：锁定基线。后续关卡、技术、美术与 Codex 执行不得擅自改写剧情事实。

### 0. 文档定位与防偏规则

本文件只负责“剧情真相”和“玩家发现真相的顺序”。它不是美术计划、技术计划，也不是关卡脚本。后续任何执行计划、CDD、场景方案、对白稿、任务配置，如果与本文件冲突，默认以本文件为准；若确实要改，必须先显式提出修改理由，再升级本文件版本。

#### 0.1 章节层级

- 大章 / Narrative Arc：类似小说一卷，是完整调查弧线。序章、第一章、第二章……终章属于这一层。

- Story Beat / 小剧情段：大章内部连续的剧情与调查节点。

- 关卡 / 任务 / 房间：制作实现单位，不在本文件锁死。

第一章、第二章都不是一个小关卡，而是大章；内部允许拆成多个小剧情、调查段和关卡。

#### 0.2 不允许的剧情漂移

- 不按“第一章夫人→第二章园丁→第三章账房→第四章柳生”轮播。

- 不按真实时间线从头顺播悲剧。

- 不改成传统“找一个凶手”。

- 不追加隐藏凶手、补刀、下毒、邪教徒、邪神解释一切。

- 主角没有推沈老爷。

- 四人不是纯恶人，也不能被完全洗白。

- “删除主角”的底层动机必须是保护。

- 认知差异不是四个人拥有四套超能力。

- 案件硬事实回答；不同人的认知都不可靠，包括玩家；终局允许多种“第五现实”结局版本，认知与现实关系保持开放。

- 大反转只保留五个，房间尺寸异常只是余刺。

### 1. 故事核心

#### 一句话故事

多年后，主角回到江南私家园林“听雨轩”调查沈老爷的雨夜死亡案；四名在场者对同一夜晚拥有互相矛盾却各自完整的认知。随着调查推进，玩家发现案发当晚还存在一个被所有证词共同删除的“第五人”，而这个人最终正是玩家自己。所有人删掉主角，并非为了陷害或抛弃，而是为了让他真正离开听雨轩、活下去。

#### 核心命题

如果记忆、感知和别人的证词都能构成不同版本的现实，你凭什么确定自己经历过的那个版本才是真的？

玩家向短句：你相信自己看到的吗？

#### 最终原则

事实层收束，认知层分歧；没有唯一被认证的 True Ending。

这里的“事实层收束”指：玩家最终应该知道主角回来过、沈老爷如何摔伤、四人如何删除痕迹、为什么延误救治。这里的“认知层分歧”指：任何人都没有完整可靠的现实版本，玩家最后拼出的第五现实也只是新的认知重构。不同玩家可以基于不同认知碎片形成不同终局，但这些终局不能互相改写案件硬事实。

### 2. 世界、案件入口与主角

- 民国十二年，中元节雨夜。

- 江南私家园林“听雨轩”。

- 沈老爷死于东院水榭，现场后来近似“无人能够进入”的密室。

- 主角是沈老爷故友留下的遗孤，自幼由沈家抚养；性别和更具体法律关系尚未锁死。

- 主角知道自己是谁，真正缺失的是：案发当晚自己其实回来过。

### 3. 案发前异常与保护计划

案发前几个月，听雨轩的现实错误逐渐集中到主角周围：房间用途记忆不一、交谈被否认、园丁记得存在的小路被别人认为是墙、旧照里的主角位置变得难以确认、相关时间与空间记录互相矛盾。

沈老爷无法判断这是记忆问题还是听雨轩本身的问题，只能确认异常在围绕主角扩大。因此决定让主角离开，并尽量切断联系。

“我不是要你消失，我是要你走得出去。”

四人分别负责：

- 沈夫人：家庭生活——收起衣物、书、用品，把旧房准备改作储藏室。

- 老周：园林空间——准备封掉主角小时候常走的隐蔽侧路。

- 钱先生：文字/制度——办理离家文件、车票、账目、身份与财务安排。

- 柳生：图像——修改家庭画像与相关画稿，让主角不再出现在沈家图像记录中。

### 4. 作者真实时间线

- 17:00 主角离开听雨轩。

- 17:30 途中打开沈老爷信件：“离开听雨轩以后，不要回来。”

- 17:40–18:00 主角把被清空的房间、被处理的名字、画像和侧路理解成“沈家要彻底赶走我”。

- 约19:00 暴雨，主角从隐蔽水榭侧路折返。

- 约19:15 经过自己的旧房，看见几乎搬空。

- 约19:30 在水榭与沈老爷争吵。沈老爷说：“我不是要你消失，我是要你走得出去。”

- 争吵后 主角转身，沈老爷追出，雨中木阶湿滑摔倒并头部受伤。主角没有推他。

- 随后 众人赶到，沈老爷仍能交流，说：“今晚，他没回来。”

- 事故后 主角从侧路离开；众人封路、清理生活痕迹、整理不在场记录、处理图像证据。

- 更晚 沈老爷伤势恶化，救治被延误，最终死亡。

没有一个简单凶手。每个人单独看都有理由，组合起来却造成不可逆悲剧。

### 5. 五种认知

#### 沈夫人：家庭生活的删除

知道主角回来、争吵和摔倒，也听见最后一句话。最初主动隐瞒是为了保护；后来逐渐真的记错。旧房变储藏室、主角坐过的位置被记成空位。

核心情感：我是在保护他。最难面对的是——自己的保护可能最终害死了丈夫。

#### 老周：空间路线的删除

知道侧路存在，看见主角回来，事故后亲手封掉。后来从“我封了这条路”变成“那晚本来就是封的”。侧路在他的认知里存在却无法抵达水榭，会回到原来的假山。

核心情感：如果我没有封那条路，一切是不是都会不一样？

#### 钱先生：文字记录的删除

事故后知道主角回来，负责整理离家时间、账册、人员记录、车票等。长期重复纸面事实后，记录比真实记忆更稳定。

核心情感：只要记录是正确的，事情就是正确的。

#### 柳生：图像与观看的删除

当晚隔着月洞门、窗框或雨幕看见模糊人影，事后才意识到可能是主角。他无法确定自己真的看见，还是后来画过以后把主角补进记忆。

核心情感：我看到的究竟是记忆，还是我后来画出来的？

#### 主角：第五份证词

玩家从第一分钟起就生活在主角版本里：相信自己没回来、侧路不存在、旧房早已改掉、案件与自己无关。

终局不是突然出现第五视角，而是发现自己一直就在第五份证词里。

#### 五种认知的共同规则

- 没有任何一份认知等于“客观地图”。

- 每份认知都至少包含一部分真实经历，也至少包含缺失、误解、补全或自我保护。

- “不可靠”不等于“随机”——每个版本必须在人物心理和经历上自洽。

- 玩家在前期可以利用不同认知解决问题；在后期必须意识到自己也一直在利用一份不可靠的第五认知。

- 终局不会把某一个角色升级为正确答案，而是让玩家用自己的行动把多份不完整认知组织成一个新的可行版本。

### 7. 五个大反转

- 不是简单撒谎，而是认知真的不同。

- 存在第五人。

- 第五人就是玩家。

- “删除玩家”不是抛弃，而是保护。

- 沈老爷不是当场被杀；掩盖玩家的行为反而延误救治。

终局房间尺寸不对只是余刺。

以上五个反转是所有结局共享的事实骨架。结局分支只能改变玩家最终如何组织这些事实、哪些认知碎片被保留以及“听雨轩究竟是什么”的解释，不能增加新的凶手、改变事故责任或推翻保护计划。

反转 = 旧证据 + 新解释。

### 13. 第四章《被删掉的人》Story Beats

- 玩家自然认为自己被集体驱逐，并保持愤怒。

- 沈夫人的物品装箱：不是毁掉，而是仔细保存。

- 老周封路。

- 钱先生准备异常周全的钱、车票、身份与账目。

- 柳生把旧画藏起来而不是烧掉。

- 沈老爷信件措辞开始不对劲。

- “我不是要你消失……我是要你走得出去。”

- 同一批证据重新解释为保护计划，但不完全洗白任何人。

- 新问题：既然我离开了，为什么案发夜又有我的脚印、茶杯和人影？

### 14. 第五章《今晚你没回来》Story Beats

- 重构自己折返的路线；第一章侧路就是自己回来时走的路。

- 恢复进入旧房、看到房间被清。

- 找到沈老爷并质问。

- 通过认知碎片拼出争吵。

- 雨中木阶事故；主角没有推人。

- 揭示沈老爷摔倒后仍活着。

- “今晚，他没回来。”完整语境。

- 玩家亲眼理解密室如何被制造：封路、清生活痕迹、整理不在场记录、处理图像证据。

- 众人忙于保护主角，沈老爷伤势恶化，救治延误。

- 没有一个简单凶手。

### 15. 终章《第五种听雨轩》Story Beats

- 不再追加隐藏凶手，不允许最后突然出现新的客观真相来源。

- 玩家确认：沈夫人、老周、钱先生、柳生四种认知都不完整；自己的“正常现实”同样只是第五份证词。

- 终局进入 Fifth Reconstruction：先搭建不可被否认的事实骨架——侧路折返、旧房、水榭入口、木阶事故、四人处理痕迹、延误救治。

- 在事实骨架成立后，允许玩家从本周目真正发现和使用过的认知碎片中继续选择、借出、锚定、保留若干互相冲突的“解释组件”。

- 玩家不是点击“相信谁”，而是用与全游戏相同的空间操作亲手完成最后一次重构。

- 系统读取 ReconstructionTrace + FinalAssembly，生成本周目的第五种听雨轩。

- 所有结局都必须给玩家一次真正的“我明白了”：案件发生了什么能够解释。

- 结局随后按重构结果进入家宅 / 路径 / 文书 / 图像 / 复合五个结局家族之一，并允许少量混合微变体。

- 没有 True Ending 标签。 复合结局也不是“最好结局”，只是更直接承认多个矛盾认知共存。

- 所有结局共享同一个极小余刺候选：内部旧房成立，但外部尺寸容纳不了；不同结局只改变玩家看到、理解和停留在这个矛盾上的方式。

- 不用恐怖音效替玩家下结论；最后的疑问是：我拼出的第五种听雨轩，是更接近现实，还是只是我自己的第五份证词？

### 16. 玩家心理曲线

好奇 → 怀疑 → 不安 → 执着 → 震动 → 愤怒 → 重新理解 → 罪责 → 理解 → 余震

### 17. 叙事验收

- 第一章后：多数人应在“有人撒谎 / 记忆有问题 / 空间不正常”，不能大量猜到主角回来。

- 第二章后：多数确认第五人存在；仅少数怀疑主角。

- 第三章后：玩家应能回想起茶杯、脚印、人影、钥匙等旧证据。

- 第四章后：理想判断是“我理解他们为什么做，但后果依然严重”。

- 结局：“沈老爷怎么死的”“第五人是谁”“删除为什么发生”答案应较一致。

- 不同玩家的终局空间、最后注视的证据和对“听雨轩是否真的受认知影响”的解释应允许明显分裂。

- 玩家应能理解“我的结局不同，是因为我亲手保留/组合了不同认知”，而不是觉得系统暗中算了一个信任分。

- 不应出现“哪个结局才是真结局”的官方标签。

### 18. 锁定与未决

#### 已锁定

章节按问题划分；时间线与发现顺序分开；每章解决一问再生新问；反转重解释旧证据；第五人=玩家由重构房间成立；删除=保护；案件高潮=重演雨夜；终局=第五种听雨轩；案件硬事实收束；所有认知包括玩家都不可靠；不同玩家的重构行为可以形成不同第五现实结局；无唯一 True Ending。

#### 阶段性

总时长、每章时长、各章 Beat 最终数量与名称、Beat 与具体关卡的对应方式、终局余刺的具体视觉表达。

#### 未决

主角性别与更细法律身份；柳生最终职业称谓；听雨轩异常起源；沈老爷医学伤情细节；终局余刺最终是否保留。

# 5. 大章、Story Beat 与可玩关卡结构

## 5.1 层级定义

- 大章 / Narrative Arc： 类似小说一卷，是完整调查弧线。

- Story Beat： 大章中的连续小剧情/调查节点。

- Level / Sequence： 实际制作单位，一个 Beat 可以跨多个房间，一个 Level 也可以承载多个 Beat。

第一章和第二章都不是“一关”，更不是十分钟原型；它们内部可以拆成 5–10 个甚至更多小段。

## 5.2 序章《回园》详细可玩 Flow

当前问题： 我为什么回来？这个案子表面上发生了什么？
认知目标： 世界基本正常。
机制目标： 教移动、调查、第三/第一人称，不正式教学 Borrow/Anchor。

主菜单
→ 雨夜正门
→ 老管家 / 提灯人带路
→ 前厅
→ 家庭旧画像
→ 离家记录
→ 西院
→ 形成窗、墙、回廊、门洞的空间记忆
→ 远看水榭
→ 水榭外围调查
→ 回访熟悉位置
→ 第一次认知异常：一扇原本存在的门消失
→ 第一章

必须埋下但不解释：老钥匙、六扇窗/外部尺寸、旧画像、离家记录、水榭位置、正常西院空间基线。

体验要求： 序章首先让玩家喜欢并记住听雨轩，而不是开场就疯狂变墙。序章结束玩家应产生“这个地方有一点不对”，而不是“这是随机换地图游戏”。

## 5.3 第一章《不存在的路》详细可玩 Flow

大章问题： 到底谁在撒谎？
核心认知： 并不是“夫人错、老周对”；两个人可能真的记得不同的园子。
使用认知： 沈夫人、老周。
正式教学： Switch → Loop → Borrowed View → Borrow → Anchor。

1-1 回到已经认识的西院
→ 1-2 墙下水痕 / 泥 / 倒灯，进入 InvestigationMode
→ 1-3 夫人认知：侧路不存在
→ 1-4 老周认知：侧路存在
→ 1-5 玩家进入侧路，假山后回到熟悉地标，确认 Loop
→ 1-6 月洞门 Borrowed View：框内出现另一认知中“正确”的直廊/可用片段
→ 1-7 Borrow：把片段带入当前世界
→ 1-8 Anchor：切认知后片段仍在
→ 1-9 打破 Loop，抵达原本不可达夹院
→ 1-10 调查旧脚印、门闩、倒灯等证据
→ 1-11 回到西院 / 建立捷径
→ 章节收束：案发夜确实有人从这条“本来不存在”的路线进入
→ 新问题：脚印是谁的？

Thought Path：

墙后可能有路
→ 谁在隐瞒？
→ 老周这里真有路
→ 为什么我又回来了？
→ 月洞门里面不是同一个空间
→ 能不能把那段空间借出来？
→ 借出来以后切换会消失
→ 那锚定以后呢？
→ 它还在
→ 我把“不存在的路”拼出来了
→ 所以案发夜真的有人从这里进入

禁止： F 标记后系统宣布“园丁说谎”；弹出“相信夫人/相信园丁”；奖励情书、带血剪刀等旧 V1 分支。

## 5.4 第二章《多出来的人》详细可玩 Flow

大章问题： 案发当晚是不是还有第五个人？
机制升级： 不再新增主系统，而是让同一套 Switch/Borrowed View/Borrow/Anchor 开始用于“证明人物存在”。
新增认知维度： 钱先生（记录）、柳生（图像/观看角度）。

2-1 第一章脚印余波
→ 2-2 前厅/生活空间出现第六只使用过的茶杯
→ 2-3 钱先生记录：主角离家时间存在修改痕迹
→ 2-4 纸面事实与空间事实冲突；理解“没有记录的东西难稳定存在”
→ 2-5 柳生雨夜画 / 月洞门特定角度出现模糊人影
→ 2-6 玩家用至少三条独立通道交叉验证
→ 2-7 自然形成错误理论：神秘第五人可能是真凶
→ 2-8 确认第五人真实存在
→ 新问题：为什么四个人都说这个人不存在？

最低证据通道：

- 空间：侧路 + 湿脚印。

- 生活物件：第六只茶杯。

- 文字：被修改的离家记录 / 账册。

- 图像：柳生特定角度的人影 / 被改画像。

玩家可漏掉其中一条，但不能因为漏一条就无法推进。

## 5.5 第三章《不存在的房间》

核心玩法不是新系统，而是扩大认知组合：四个版本分别保留门、窗、边界、旧走廊等部分，玩家亲手重构一个“谁都没有完整记住”的普通儿童房。老钥匙打开床板下盒子，玩家自己得出“这是我的房间 → 第五人就是我”。

## 5.6 第四章《被删掉的人》

玩法核心是 Evidence Recontextualization：同样的装箱、封路、钱、车票、画像从“驱逐/掩盖犯罪”重新解释为保护计划，但不洗白后果。玩家应停在“我理解他们为什么做，但结果依然严重”。

## 5.7 第五章《今晚你没回来》

通过 Scripted Reconstruction 重走侧路、旧房、水榭、争吵和木阶事故。明确主角没有推沈老爷；摔倒后沈老爷仍能交流；“今晚，他没回来”成为保护主角的请求；玩家亲眼看着封路、清痕迹、改记录、改图像如何最终制造“密室”，并理解保护行动客观延误救治。

## 5.8 终章《第五种听雨轩》

玩家把四份认知和自己的认知组合成能解释侧路、旧房、水榭入口、行动路线和死亡过程的第五现实。终局分两层：

- Fact Skeleton： 所有玩家必须亲手拼出同一组案件硬事实，保证叙事收束。

- Cognitive Assembly： 在硬事实成立后，玩家继续用 Borrow / Anchor / Reconstruction 选择保留哪些认知碎片。此前发现的可选证据、使用过的替代解和锚定历史会影响可用组件，但不会暗中单独决定结局。

最终生成家宅 / 路径 / 文书 / 图像 / 复合五个结局家族之一。没有 True Ending；不同结局不是不同凶手或不同死亡事实，而是玩家对同一事实构造出的不同第五现实。所有结局都可保留“内部旧房成立、外部尺寸容不下”的同一余刺候选。

# 6. 听雨轩世界拓扑与关卡空间

## 6.1 Master Topology

当前基础世界应形成一座完整、可重访、可形成地标记忆的园林：

正门
↓
前厅 ───────── 北楼 / 账房
↓
西院 ── 曲廊 ── 假山 / 侧路 / 夹院
↓ ↓
内宅 / 旧居 水院 ── 桥 ── 水榭

关键要求：

- 水榭从早期多个位置可见，但不立刻可达。

- 西院、曲廊、假山、水院、北楼、内宅必须一眼可分辨。

- 园林不是一条串联走廊；必须有框景、遮挡、转折、开院、视线切片和回访捷径。

- 空间先具备“正常版本”，认知异常才有对照。

## 6.2 区域功能表

- 区域： 正门； 叙事功能： 主角归园； Gameplay 功能： 第三人称进入、NPC 引导； Art 功能： 第一印象：真实江南宅园

- 区域： 前厅； 叙事功能： 家庭关系、画像、记录； Gameplay 功能： 基础调查、茶杯、文档； Art 功能： 生活痕迹与家族秩序

- 区域： 西院； 叙事功能： 正常空间基线； Gameplay 功能： 第一章主区； Art 功能： 玩家必须记住的“可靠现实”

- 区域： 曲廊； 叙事功能： 方向感与重访； Gameplay 功能： Switch / 框景 /路径变化； Art 功能： 形成层层遮挡和节奏

- 区域： 假山； 叙事功能： 老周空间认知； Gameplay 功能： Loop / 侧路； Art 功能： 遮挡传送、窄口、湿石

- 区域： 夹院； 叙事功能： 隐藏事实区； Gameplay 功能： 脚印/门闩证据； Art 功能： 安静、小、被遗忘

- 区域： 水院； 叙事功能： 长期目标前庭； Gameplay 功能： Bridge/Borrow 扩展； Art 功能： 水面、反射、远景水榭

- 区域： 水榭； 叙事功能： 案件中心； Gameplay 功能： 第五章重演； Art 功能： 既熟悉又最终令人不安

- 区域： 北楼； 叙事功能： 钱先生记录； Gameplay 功能： 文档/账册/高处观看； Art 功能： 稳定、规整、纸面秩序

- 区域： 内宅/旧居； 叙事功能： 主角身份； Gameplay 功能： 不存在的房间； Art 功能： 普通生活空间，避免“鬼屋化”

# 7. Art Direction：美术不是模型列表

## 7.1 核心定义

模型不是美术结果；模型是美术实现所使用的生产素材。

Art Direction 决定目标，Modeling 提供形体，Environment Art 组织空间，Lighting / Dressing 让场景最终成立。

正确生产链：

剧情 / Gameplay 目标
→ Level 功能
→ Visual Brief：这一段要让玩家看见和感到什么
→ Composition / Reference Target
→ Asset Brief：需要哪些模型、材质、道具
→ 下载 / 自制 / 修改
→ Environment Assembly
→ Material Harmonization
→ Dressing
→ Lighting / Rain / Fog
→ Cognition Variant
→ Screenshot / Playtest Gate

禁止：下载一个高质量模型 → 直接丢进 Three.js → 认为“美术完成”。

## 7.2 视觉关键词 [LOCKED]

- 民国江南私家园林。

- 中式，不做泛日式神社语言。

- 中元雨夜。

- 潮湿、灰瓦、白墙、深旧木。

- 雨打石板、墙根水痕、苔藓、旧木吸水。

- 小面积暖灯，大面积冷暗环境。

- 真实空间先成立。

- 恐怖来自熟悉空间慢慢不可信。

- 不做满屏血、红灯、鬼脸。

- 不做廉价绿色滤镜。

- 不做赛博金色 HUD。

UI 次级 #817F7A

## 7.4 构图规则

每 8–12 米场景段至少引入 2–4 个变化来源：

- 道路方向改变；

- 视线打开/关闭；

- 院墙/漏窗变化；

- 树木遮挡；

- 地面材质变化；

- 前景道具；

- 高低差；

- 水面/反射；

- 屋檐压景；

- 远处地标。

回廊禁止连续复制完全相同的柱距、窗格和灯笼节奏。

## 7.5 认知版本的美术规则

共享 70–90% 基础正式场景。不同认知优先改变空间事实和生活状态，不是整套换皮。终章的不同结局同样复用同一套正式听雨轩资产，通过“保留了哪些认知变体、哪些空间连接、哪些证据/声场/陈设成为主导”产生差异，不为每个结局另做一张完整地图：

### 主角 / 当前世界

中性、可信、现实感最强。玩家默认“这就是客观现实”。

### 沈夫人

家庭秩序与生活痕迹：房间用途、收纳、茶杯、椅子、物品摆放、主角位置是否为空。可以略更整齐、稳定，但不把全图刷成红金主题。

### 老周

路线、封路与维护痕迹：侧路、假山连接、木板、泥、封堵、植物覆盖、修补痕迹。重点是可走性变化，不是“绿色滤镜”。

### 钱先生

记录和制度痕迹：建筑图、账册、标签、登记与未登记对象的稳定程度。可用秩序、重复、纸张与墨线强化，但不做数字 HUD 覆盖世界。

### 柳生

框景、观看角度与图像不可靠：特定月洞门/窗框角度成立，换角度后断裂；画像与草图的构图影响玩家观看。可以有极轻的画面纹理倾向，但不把整张地图变油画 Shader。

## 7.6 灯光与天气

- 冷环境光提供可读暗部。

- 灯笼/室内提供少量暖光，不承担全局照明。

- 雨、雾、水汽负责远景衰减，而不是纯黑 void。

- 湿地通过 roughness、normal、puddle decal 表现，不把地面变镜子。

- 水榭与水院需要空气层、倒影和雨点，但控制 SSR/反射成本。

- 认知切换的 VFX 只辅助，不得比真实空间变化更抢眼。

# 8. Modeling / Asset Production 与 Environment Art 协作规范

## 8.1 四层生产结构

Art Direction
↓
Gameplay Skeleton ↔ Visual Assets
↓
Environment Assembly
↓
Procedural Dressing / Lighting / Cognition Variant
↓
Final Scene

### Layer A — Gameplay Skeleton

只负责 Collision、Trigger、Navigation、NPC 路线、任务点、门交互范围、Cognition 区域、Borrow/Anchor 逻辑。默认隐藏。

### Layer B — Visual Assets

GLB/glTF、Blender 清洗后的真实模型、PBR 材质。房屋、回廊、月洞门、门窗、水榭、桥、假山、家具、关键道具都属于这里。

### Environment Assembly

这是之前最缺的一层：决定模型如何拼成“园林”，包括比例、地基、水岸、遮挡、视线、前中远景、道具密度、生活痕迹、风格统一。

### Layer C — Procedural Dressing

Three.js 适合做雨、雾、落叶、小石头随机、植被变化、水渍、苔藓、灯光、局部破损、认知差异辅助。程序 Dressing 不能替代 Hero 建筑视觉。

## 8.2 下载模型的默认处理原则

对于 Asset Preview 已证明达到正式视觉质量的下载模型：

默认“直接使用 + 最小必要处理”，不是“删掉原几何后用 Box/Cylinder 重建”。

允许：

- 整组直接使用；

- 按区域切分；

- 删除真正无用节点；

- Scale / Pivot 修正；

- Material cleanup；

- Texture compression；

- 必要 Decimate；

- Collision proxy；

- LOD；

- runtime 文件拆分。

禁止：

- 为了统一模块尺寸把高质量建筑几何程序低模化；

- 为了 18 MiB / 25 MiB 猜测性预算用方盒替代正式模型；

- 在真实浏览器没有性能数据前大规模减面。

# 9. 各区域 Art × Modeling × Gameplay 统一 Brief

## 9.1 正门

- 叙事： 多年后归园，第一印象必须可信。

- Gameplay： 第三人称进入、管家引导、最简单互动。

- Art： 深色门、灰瓦、湿石、少量暖灯，雨外强、檐内弱。

- Modeling： 优先使用完整 Siheyuan 门/前厅建筑组或高质量原件区域，不得用程序方框承担近景。

- Dressing： 门槛水痕、灯笼、排水、墙根苔藓、少量杂物。

## 9.2 前厅

- 叙事： 家庭画像、离家记录、茶杯，建立沈家生活。

- Gameplay： InvestigationMode、文档、物件观察。

- Art： 不做废墟；仍能看出曾经有人长期生活。

- Modeling： 主屋整组 + 八仙桌/椅/画像位/柜体。

- 未来认知： 沈夫人主要改生活痕迹；钱先生改记录稳定性。

## 9.3 西院

- 叙事： 序章的“正常现实基线”，第一章再打破。

- Gameplay： 第一章核心入口。

- Art： 玩家必须能记住窗、墙、门洞、树和主屋关系。

- Modeling： Courtyard Park 空间语言 + 正式房屋；至少一次开院、一个视觉地标。

- Cognition： 侧路有/无、物件位置和生活痕迹改变，而不是颜色换皮。

## 9.4 曲廊 / 月洞门

- Gameplay： Borrowed View 核心展示；第三/第一人称转换。

- Art： 真实瓦顶、柱梁、漏窗，不允许程序低模承担玩家近景。

- Modeling： Courtyard Park 回廊构件；Gameplay Moon Gate 单独控制尺寸和 Portal Surface。

- Composition： 月洞门后必须有可识别地标，才能让“里面是另一现实”一眼可懂。

## 9.5 假山 / 侧路

- Gameplay： Loop、遮挡传送、第一章路线重构。

- Art： “看得见但走不到”“绕”“藏”，避免一块巨大单模型摆中央。

- Modeling： 岩石组 + gameplay geometry 组合；必须形成洞口、夹道、视线切片、高低差。

- Audio： 雨声/水声方向用于掩盖 Loop 连续性。

## 9.6 夹院

- 叙事： 脚印、门闩、弱证据；不能放凶器和直接身份答案。

- Art： 小、静、潮湿、像被遗忘的服务空间。

- Modeling： 自制/轻量组合，重点地面和门闩互动。

## 9.7 水院 / 桥 / 水榭

- 叙事： 水榭是长期目标，第一小时就能看到但不能直接进入。

- Gameplay： 后续 Borrow/Bridge、第五章重演。

- Art： 水面不镜面化；桥、水岸、亭子必须落地衔接，不漂浮。

- Modeling： Low Bridge + Pavilion/Pavilion Memoriam；水岸和地基需要 Environment Art 重做，而不是只给位置/缩放。

## 9.8 北楼

- 叙事： 钱先生记录空间。

- Gameplay： 文档、楼层高差、从二层反看园林。

- Art： 稳定、规整，但仍是同一听雨轩，不变成赛博账本世界。

- Modeling： House/Siheyuan 组件，内部至少一层可进入。

## 9.9 内宅 / 旧居 / 不存在的房间

- 叙事： 第三章身份反转。

- Art： 旧房最终必须普通、甚至温柔，反差比“鬼屋”更重要。

- Modeling： 外墙长度、窗数、柱距从早期就固定，为尺寸矛盾提供客观基线。

- Tech： 必要时用 Portal Interior / separate interior scene 制造内部容积不可能，而不是硬塞 Mesh。

# 10. Character、Camera、Animation 与 NPC

## 10.1 Camera

长期锁定：第三人称主探索 + 第一人称调查/强谜题。 当前若仍第一人称可用于短期资产验证，但环境尺度、碰撞、门廊宽度和相机净空必须兼容未来第三人称。

## 10.2 角色占位与动画

第一阶段允许合法 Mixamo 占位角色，状态：Idle / Walk / Fast Walk / Run / Turn / Stop / Look / Inspect。正式民国服装以后替换模型，Camera/Controller/Animation Mapping 不重写。

## 10.3 身体交互

至少：推门、拉门、查看物品、拿证据、靠近漏窗、门闩、提/点灯、触摸墙面水痕。世界反馈优先于 UI 卡片。

## 10.4 NPC 引导

序章老管家/提灯人采用简单 waypoint GuideSequence，不做通用 AI：玩家落后时等候、关键节点停下、LookTarget、对话触发、提灯绑定 socket。

# 12. Audio Design

## 12.1 设计原则

- 空间即声音：不同区域闭眼也能分辨。

- 认知差异可听，但不做科幻能量门。

- 沉默和动态范围比全程恐怖 BGM 更重要。

## 12.2 Zone

FrontHall / WestCourt / Corridor / Rockery / WaterCourt / Interior / SideYard。

雨打瓦、叶、石，滴水、风、远水、木构轻响、远门声通过 PositionalAudio / Web Audio crossfade 组织。

## 12.3 脚步材质

WetStone / Wood / Mud / InteriorWood / Puddle；跨材质 1–2 步应能听出变化。

## 12.4 核心机制声效语言

- Switch：环境声短暂错位。

- Borrowed View：框内可以听到另一认知的局部声场。

- Anchor：声音更“固定/静止”。

- Loop：方向感产生轻微异常，但不直接提示传送。

## 12.5 音乐

正常探索少音乐；认知不安用低密度 texture；证据区优先环境声；反转可有短主题，避免全程恐怖循环音乐。

## 12.6 资源

Sonniss GDC 2026 Bundle 作为优先免费 royalty-free 音效来源；项目建立来源/许可记录。

# 13. Technical Architecture

## 13.1 当前基础

- Three.js / WebGPURenderer。

- Rapier WASM 物理。

- Vite Web 项目。

- Runtime GLB/KTX2/Meshopt 资产管线已经存在。

- 当前场景已经有 gameplaySkeleton / visualAssets / proceduralDressing 三个根组。

旧 V1 曾规定 Zustand/PWA/Git LFS 等。是否继续使用必须以仓库现实为准，不因旧文档强行引入。

## 13.2 数据驱动

场景坐标、anchor、collider、trigger、DoorState、CognitionState、Evidence、NarrativeGate、ReconstructionTrace、FinalAssemblyState 都应数据化，避免章节脚本继续堆硬编码坐标和条件。

## 13.3 Save

必须保存：chapter / beat / playerTransform / currentCognition / discoveredEvidence / optionalEvidence / puzzleStates / anchorSlot / anchoredFragments / reconstructionTrace / finalAssemblyState / openedDoors / narrativeGates / layoutVersion。

不保存整棵 runtime Mesh JSON；读取时按逻辑 id 重建。

## 13.4 Debug

开发模式至少显示：Current Cognition、Current Beat、Player Position、Active Portal Count、Anchor State、Evidence、Puzzle State、ReconstructionTrace、Current Ending Lens（仅 Debug）、FPS、Frame Time、Draw Calls、Triangles、Loaded Assets。正式 UI 不显示任何“信任分 / 结局分”。

## 13.5 WebGPU / WebGL2

WebGPU 是主要目标；关键基础流程应有 WebGL2 fallback 或清晰的不可用提示。Borrowed View 若 WebGPU 特性不足，降级方案优先是低分辨率/静态局部展示，而不是黑屏。

## 13.6 性能原则

先把正式效果做出来
→ 浏览器 Profile
→ 找真正瓶颈
→ 针对优化

25 MiB：当前 Cloudflare Pages 发布路径的单 runtime 文件约束，不是源模型或视觉质量限制。超出优先 split、共享纹理、KTX2、Meshopt/Draco、deferred loading、LOD；必要时再考虑 R2/其他静态存储。

18 MiB：只作首屏 profiling target，不再作为构建硬失败门槛。

## 14.6 25 MiB / 18 MiB 的真实含义

### 25 MiB

当前仓库把 25 MiB 写成了 runtime / public 文件硬门禁。该限制来源于当前 Cloudflare Pages 发布路径的单静态文件约束，但它只能约束最终 runtime chunk，不能反向变成源模型、艺术质量或“必须低模”的理由。

正确处理：split / KTX2 / Meshopt / Draco / deferred loading / LOD；必要时再考虑 R2/其他静态存储。

### 18 MiB

initialBudgetMb: 18 原本只是章节首屏预算元数据；本轮实现把它额外硬编码为构建失败条件。V4 将其恢复为profiling target / warning，不再作为艺术设计硬门槛。

# 21. 历史设计归档：为什么旧 V1 不再是当前游戏

旧 V1 的核心是“走 → 切记忆 → 勘误 → 信任选择 → 世界按被信任者重构”，并包含 Truth Matrix、Trust Nodes、Cognitive Backlash、Past/Present 时间线、四套独立 L3 物理法则、隐藏第五视角/多真相结局等。它为项目提供了很多重要母体：园林、四视角、死循环、Portal、空间证词、不可靠叙事。

当前 V4 不否定这些历史贡献，但产品已经发生以下本质升级：

- 从“证明谁说谎” → “利用不同认知解决问题”。

- 从“系统判真假” → “玩家自己建立理论”。

- 从“选择相信谁” → “组合多个认知，没有一个人拥有完整答案”。

- 从“过去/现在 Portal” → “认知与认知的 Borrowed View”。

- 从“四个独立秘密” → “四个人共同执行一个保护计划”。

- 从“隐藏第五视角” → “玩家从第一分钟就在第五份证词里”。

- 从“真相不可知” → “案件事实清楚，现实解释开放”。

因此旧 V1 的底层技术可以继续用，旧业务规则不能继续自动扩张。

后续 Codex 开发必须同时遵守：

- 《游园惊梦：四面证词》剧情母文档 V3.0 · Narrative Source of Truth

## 0. 当前开发总原则

### 0.1 能抄成熟机制，就不重新造轮子

项目只把开发资源花在真正属于《游园惊梦》的部分：

- 认知版本如何组织；

- 借景能借什么；

- 锚定如何改变谜题；

- 不同认知怎样形成案件证据；

- 如何把玩法与剧情反转咬合；

- 听雨轩空间如何让玩家产生认知。

以下通用问题优先直接复用成熟实现：

- 通用问题： Web 3D 渲染； 优先方案： 当前 Three.js WebGPURenderer

- 通用问题： 第三人称相机平滑控制； 优先方案： camera-controls

- 通用问题： 角色移动 / move-and-slide / 台阶 / 坡面； 优先方案： Rapier Kinematic Character Controller

- 通用问题： 角色 / 相机碰撞； 优先方案： Rapier ray cast / shape cast

- 通用问题： 月洞门看另一现实； 优先方案： Three.js 官方 webgpu_portal / WebGPU render pass 思路

- 通用问题： 交互拾取； 优先方案： Three.js Raycaster

- 通用问题： 角色动画； 优先方案： Mixamo + Three.js AnimationMixer

- 通用问题： 空间音频； 优先方案： Three.js AudioListener / PositionalAudio + Web Audio

- 通用问题： GLB / KTX2 / Meshopt； 优先方案： 当前项目已有 RuntimeAssetLoader 管线

- 通用问题： 自动截图； 优先方案： 优先复用现有 Playwright / E2E；没有才补最小脚本

- 通用问题： UI； 优先方案： 复用项目现有 Web UI / React/CSS 架构，不另起 UI 框架

## 2. 系统架构：不要复制四张地图

### 2.1 世界结构

统一一座听雨轩：

TingYuXuanWorld
├── sharedWorld
│ ├── terrain
│ ├── permanent architecture
│ └── shared props
│
├── cognition
│ ├── protagonist
│ ├── wife
│ ├── gardener
│ ├── accountant
│ └── artist
│
├── borrowedLayer
├── anchoredLayer
├── interactionLayer
├── gameplaySkeleton
└── proceduralDressing

#### 原则

不是：

WifeScene.glb
GardenerScene.glb
AccountantScene.glb
ArtistScene.glb

四张完全复制的地图。

而是：

一套共享基础空间 + 各 Cognition 的差异对象 / 差异状态。

### 2.2 Cognition Object Schema

建议：

type CognitionId =
| 'protagonist'
| 'wife'
| 'gardener'
| 'accountant'
| 'artist';

interface CognitionObject {
id: string;
baseAssetId?: string;

states: Partial<Record<CognitionId, {
visible?: boolean;
position?: [number, number, number];
rotation?: [number, number, number];
scale?: [number, number, number];

materialVariant?: string;
colliderEnabled?: boolean;
interactionEnabled?: boolean;

lightPreset?: string;
audioPreset?: string;
}>>;

borrowable?: BorrowableConfig;
}

不允许在场景逻辑中继续堆：

if (wife) ...
if (gardener) ...
if (chapter === 2 && ...)

## 3. 第三人称主探索系统

### 3.1 玩家体验

正常状态：

第三人称肩后 / 略居中探索。

承担：

- 园林移动；

- 形成空间记忆；

- 看水榭远景；

- 跟随 NPC；

- 识别地标；

- 看到自己与空间关系。

### 3.2 软件实现

#### 直接复用：camera-controls

用途：

- camera target；

- smooth transition；

- shoulder offset；

- 进入室内后的距离变化；

- 第三 → 第一人称过渡；

- 第一 → 第三人称恢复；

- 章节演出镜头的轻微 reposition。

不要自己写一整套 camera damping。

#### Camera Collision

使用 Rapier：

Player / Shoulder Target
↓ shape cast / ray cast
Desired Camera Position

命中墙 / 柱：

desiredDistance → safeDistance

不修改玩家世界坐标。

### 3.3 验收

连续走：

- 正门

- 西院

- 曲廊

- 假山

- 室内

5 分钟：

- 无频繁穿墙；

- 不猛烈甩镜；

- 角色不长期遮住调查对象；

- 窄廊自动合理缩短镜头。

## 4. 第一人称 Investigation Mode

### 4.1 用途

仅用于：

- 脚印；

- 水痕；

- 门闩；

- 旧画像；

- 离家记录；

- 茶杯；

- 月洞门 / 漏窗；

- 精确借景；

- 强空间谜题。

不承担整个游戏普通移动。

### 4.2 软件实现

#### 相机

仍使用同一 Camera + camera-controls transition。

Exploration Camera Pose
↓ 200–450 ms
Investigation Camera Pose

进入：

- 隐藏头 / 会挡镜头的上身部分；

- 锁定不允许作弊穿过 collider；

- 可以保留手部 / 阴影。

退出：

- 回到第三人称原方向；

- 角色动画不被 reset。

#### 拾取

直接用 Three.js Raycaster：

screen center
→ Interactable Layer
→ nearest hit
→ InteractionController

Raycaster 只看指定 Layer，避免扫全场景。

## 6. 认知切换 Cognition Switch

### 6.1 玩家体验

不是：

屏幕闪一下，套一个绿色滤镜。

应该是：

空间连续，但门、墙、道路、物体、灯、声音、碰撞真正改变。

关闭特效后仍必须看得懂世界已经变化。

### 6.2 软件实现

CognitionController：

class CognitionController {
current: CognitionId;

setCognition(next: CognitionId) {
// visual
// collider
// interactable
// light
// audio
// puzzle state hooks
}
}

切换：

- 更新 Cognition Group / Object State；

- 启用 / 禁用对应 Rapier collider；

- 更新 interaction registry；

- light preset crossfade；

- audio preset crossfade；

- 非必要不 reload GLB。

### 6.3 自动异常

只允许少量 scripted event：

例如：

序章结尾，熟悉位置的一扇门消失。

大部分认知变化由玩家主动触发。

## 7. Borrowed View / 借景

这是本项目最需要“借成熟实现”的技术之一。

### 7.1 玩家体验

站在当前认知中。

透过：

- 月洞门；

- 漏窗；

- 屏风；

- 特定窗框；

直接看到：

同一位置的另一认知版本。

左右移动时，框内视差必须自然。

不能只是贴一张截图。

### 7.2 软件实现基线

#### 优先参考 Three.js 官方 WebGPU Portal Example

官方例子已经证明：

Portal 可以显示另一个 scene。

本项目无需从零研究“怎么把另一场景渲染到面上”。

第一版采用 WebGPU render pass / portal surface 思路。

#### 本项目进一步简化

因为多个 Cognition 共用听雨轩世界坐标：

不需要第一版就做复杂的“Portal A ↔ Portal B 任意坐标转换”。

可以：

Current Cognition
+
Main Camera
↓

Portal Surface
↓ render target / pass

Target Cognition Group
+
same / derived Camera

### 7.3 Portal Component

BorrowedViewFrame
├── frameVisual
├── portalSurface
├── portalCameraBinding
├── visibilityMask
├── sensor
└── borrowTargetRegistry

### 7.4 性能规则

第一版：

- 同屏最多 1–2 个 Active Portal；

- 离玩家太远禁用 portal render；

- 被墙完全遮挡则暂停；

- Portal resolution 可独立缩放；

- Portal 不递归渲染 Portal。

### 7.5 验收

30 秒演示：

不解释术语，旁观者能自己说出“门里面看到的是另一个版本”。

## 8. Loop Space / 假山回环

### 8.1 玩家体验

老周认知：

侧路明明存在。

但是：

玩家穿过假山，最后又回到了熟悉地标。

第一次反应应该是：

“我怎么又回来了？”

而不是：

“刚才被游戏传送了。”

### 8.2 第一版不要做递归 Portal

优先：

Occlusion + Rapier Sensor + Paired Transform Teleport。

流程：

玩家进入假山遮挡 / 转角
↓
LoopEntry Sensor
↓
position / yaw 映射
↓
LoopExit
↓
保持声音连续
↓
重新看到熟悉地标

### 8.3 LoopLink

interface LoopLink {
entrySensorId: string;
exitAnchorId: string;
preserveYaw: boolean;
preserveVelocityIntent: boolean;
cooldownMs: number;
}

需要 cooldown 防止反复触发。

### 8.4 如果第一版穿帮

升级顺序：

- 改善遮挡；

- 改善地标布局；

- 预加载出口场景；

- 相机 transform continuity；

- 最后才考虑完整 Portal teleport。

## 9. Borrow / 借出

### 9.1 不是“任意物体抓出来”

第一版只有白名单：

StoneSlab
BridgeSegment
CorridorSegment
DoorState

### 9.2 软件实现

interface BorrowableConfig {
sourceCognition: CognitionId;
runtimePrefabId: string;
collisionPrefabId: string;
allowedTargetAnchors: string[];
}

Borrow 后：

Source Cognition Object
↓
BorrowController
↓
borrowedLayer Runtime Instance
+
Rapier Collider

不是简单复制 Scene Mesh。

### 9.3 视觉反馈

玩家必须能直接看到：

“我把另一个现实里的东西带出来了。”

不要主要靠 HUD 文本。

可以使用：

- 结构逐渐稳定；

- 湿痕 / 灰尘 / 雨水短暂错位；

- 声音切换；

- 很轻的材质边缘过渡。

不要科幻粒子门。

## 10. Anchor / 锚定

### 10.1 规则

第一版：

1 个 Anchor Slot。

Borrowed object 未 Anchor：

切 Cognition 后消失 / 恢复来源规则。

Anchor 后：

跨 Cognition 保留。

### 10.2 数据

interface AnchorSlot {
borrowedObjectId: string | null;
sourceCognition?: CognitionId;
targetAnchorId?: string;
}

### 10.3 Softlock

必须支持：

- 解除锚定；

- Puzzle reset；

- anchor 回收；

- 安全 checkpoint；

- 如果玩家掉入无出口区域，恢复到最近 SafeAnchor。

### 10.4 核心验收

A 认知看到桥
→ Borrow
→ Anchor
→ Switch B
→ 桥仍然存在
→ 玩家真实踩上桥
→ Collider 正确

## 11. 多解谜题框架

### 11.1 谜题不是一个 Scripted Sequence

建议每个 Puzzle：

interface PuzzleDefinition {
id: string;
inputs: PuzzleCondition[];
worldStates: PuzzleWorldState[];
solutions: PuzzleSolution[];
evidenceRewards: string[];
resetPolicy: ResetPolicy;
}

### 11.2 第一阶段要求

至少一个谜题允许：

#### 解法 A

借直廊 → Anchor → 打破循环。

#### 替代解入口

例如借石板 / 门状态形成另一条局部路线。

不要求第一版就做十种 Sandbox 解。

## 12. Evidence System / 调查证据

### 12.1 系统只保存事实，不替玩家宣布结论

Evidence：

interface Evidence {
id: string;
discovered: boolean;

observableFacts: string[];
currentContext?: string[];

narrativeTags: string[];
}

不要：

Evidence: 老周说谎 +1

### 12.2 多通道证据

重大结论至少来自三个通道：

- 空间；

- 物体；

- 文字 / 图像 / 人物。

第二章：

湿脚印
+
第六只茶杯
+
被修改记录
+
柳生模糊人影

玩家可以漏一项，不应该因此剧情崩溃。

## 13. Evidence Recontextualization / 二次解释

这是整个剧情最重要的软件需求之一。

同一个 Evidence 不应该被后面删除再换一个新 Evidence。

例如：

离家记录

前期：

主角当天已经离开。

第二章：

有修改痕迹，可能有人掩盖犯罪。

第四章：

钱先生在给主角制造不在场证明 / 安排离开。

### 13.1 数据方式

interface EvidenceInterpretation {
unlockCondition: string;
text: string;
}

interface Evidence {
facts: string[];
interpretations: EvidenceInterpretation[];
}

facts 永远不改。

变化的是：

interpretation。

符合剧情母文档的：

反转 = 旧证据 + 新解释。

## 14. Narrative Gate / 半开放调查

### 14.1 不做完全开放信息网

章节内部可以：

- 不同证据顺序；

- 多路线；

- 多解法。

但是关键认知跃迁有顺序：

认知不同
↓
第五人存在
↓
第五人 = 玩家
↓
删除 = 保护
↓
事故 + 延误救治

### 14.2 实现

不要在代码里散落：

if (foundCup && foundFootprint && ...)

建立：

NarrativeGate {
id
requiredAny
requiredAll
minEvidenceChannels
unlockBeat
}

例如：

CH2_FIFTH_PERSON_CONFIRMED

条件：

至少 3 个独立 Evidence Channel 已满足。

## 15. Thought Path 作为 QA 系统，而不是 UI

玩家不看到 Thought Path。

开发者要维护：

Observation
→ Hypothesis
→ Experiment
→ New Fact
→ Updated Hypothesis

第一章：

墙后有异常
→ 有人说谎？
→ 比较两认知
→ 老周路会循环
→ 月洞门看到另一版本
→ 借出 + Anchor
→ 路真的能成立
→ 案发夜有人从这里进入

### QA 测试时记录

- 玩家在哪一步形成假设；

- 哪一步卡住；

- 是否跳过关键推理；

- 是否被 UI 直接告诉答案；

- 是否过早猜中主角回来。

## 16. 四种认知不做“四套超能力”

四人区别主要通过：

内容、空间状态和证据呈现。

而不是四套新引擎。

### 16.1 沈夫人：家庭生活

表现工具：

- 房间用途；

- 桌椅；

- 茶杯；

- 物品是否存在；

- 旧房 → 储藏；

- 家庭生活痕迹。

软件：

CognitionState + Prop Variant。

不开发专属 Physics。

### 16.2 老周：空间路线

表现：

- 侧路；

- 封路；

- Loop；

- 路径连接关系。

软件：

CognitionState + Collider State + LoopLink。

### 16.3 钱先生：文字 / 制度

表现：

- 建筑图；

- 账册；

- 离家记录；

- 有记录的空间稳定；

- 未记录的信息缺失 / 模糊。

软件：

- Evidence / Document UI；

- CognitionState；

- 特定 Object visibility。

不需要开发“文字改变现实”的全新物理引擎。

### 16.4 柳生：图像 / 观看角度

表现：

特定视角下，人影 / 走廊 / 图像才成立。

第一版实现：

- Camera angle cone；

- Portal frame；

- visibility condition；

- view-dependent trigger。

ViewCondition {
cameraPositionZone
lookDirection
targetAngleTolerance
}

满足时：

object visible / evidence valid。

不需要完整 ray-traced hallucination system。

## 17. View-dependent Evidence / 特定角度证据

用于第二章柳生。

流程：

普通位置
→ 看不清
→ 玩家移动到月洞门框景
→ 角度匹配
→ 模糊人影成立
→ 离开角度
→ 又不成立

软件：

- Camera world position；

- view direction；

- dot product；

- visibility threshold；

- Raycaster occlusion。

## 18. 第三章：不存在的房间

虽然当前先开发序章 / 第一 / 第二章，但系统必须为第三章留接口。

玩家从四种 Cognition 借：

- 门；

- 窗；

- 房间边界；

- 旧走廊。

组合成：

谁都没有完整记得的房间。

实现不新增新主系统。

复用：

+

+

这证明核心玩法有扩展性。

## 19. 第五种现实 Reconstruction Mode / Reconstruction Ending System

后期不是“选择一个认知作为正确答案”，也不是恢复旧 Trust Node。

而是：

玩家先亲手拼出所有结局共享的案件 Fact Skeleton，再把多个不完整认知组件组合成自己的第五种听雨轩。

软件上：

anchoredLayer
+
reconstructionPuzzleState
+
multiple borrowed components
+
ReconstructionTrace
+
FinalAssemblyState

建议接口：

interface ReconstructionTrace {
discoveredOptionalEvidence: string[];
solvedWithCognition: Record<string, string[]>;
anchoredFragments: string[];
preservedContradictions: string[];
finalAssemblyFragments: string[];
}

type EndingLens =
| 'domestic'
| 'spatial'
| 'documentary'
| 'pictorial'
| 'composite';

interface FinalAssemblyState {
factSkeletonComplete: boolean;
selectedFragments: string[];
endingLens: EndingLens;
}

规则：

- factSkeletonComplete 不允许分支：主角回来、摔伤、未推人、删除痕迹、延误救治必须成立。

- ReconstructionTrace 记录行为，不记录“相信谁 +N”。

- 早期轨迹影响终局可用碎片与微变体，不可单独暗算结局。

- Final Assembly 必须由玩家在世界内亲手完成。

- 输出家宅 / 路径 / 文书 / 图像 / 复合五个结局家族；没有 True Ending。

- 第一阶段核心 Vertical Slice 只留数据接口，不现在开发完整终章。

- 中文： 借景； 英文： Borrowed View； 当前定义： 通过框景实时看到另一 Cognition 的局部世界

- 中文： 借出； 英文： Borrow； 当前定义： 把另一 Cognition 的白名单对象/空间状态带入当前世界

- 中文： 锚定； 英文： Anchor； 当前定义： 让 Borrowed Object 跨 Cognition 继续存在

- 中文： 回环； 英文： Loop Space； 当前定义： 玩家行走后在无明显黑屏传送下回到熟悉空间

- 中文： 第五种听雨轩； 英文： Fifth Reconstruction； 当前定义： 玩家组合多个认知形成的解释性现实，不等于绝对客观真相

- 中文： Evidence； 英文： 证据； 当前定义： 可观察事实，不直接包含系统推理结论

- 中文： Recontextualization； 英文： 二次解释； 当前定义： 同一证据事实不变，后期 interpretation 改变

- 中文： Narrative Gate； 英文： 叙事门槛； 当前定义： 通过多个证据通道控制关键揭示顺序

- 中文： Gameplay Skeleton； 英文： 游戏骨架； 当前定义： 隐形碰撞/Trigger/Nav/任务/机制坐标

- 中文： Visual Asset； 英文： 正式视觉资产； 当前定义： 玩家实际看到的高质量模型和材质

- 中文： Environment Art； 英文： 场景美术组装； 当前定义： 把资产组织为有构图、生活密度和叙事功能的最终场景

- 中文： Procedural Dressing； 英文： 程序化装饰； 当前定义： 雨、雾、植被变化、水渍、苔藓、灯光等可程序生成层

# 附录 D：团队开工前必须回答的 10 个问题

每次新增章节/系统前，负责人必须先回答：

- 这项工作服务哪个 Story Beat / 玩家问题？

- 玩家实际做什么，而不是 UI 显示什么？

- 结果改变了世界、证据还是玩家理解？

- 是否已有成熟库/仓库代码能复用？

- 是否在重复开发已经完成的 Loader/Physics/Camera/Asset Pipeline？

- 这一段 Art Brief 是什么？

- 需要哪些正式模型，哪些只是 Gameplay Skeleton？

- Cognition Variant 改的是空间事实还是只换滤镜？

- 如何截图/录像/Playtest 验收？

- 如果做完后普通玩家仍感到“灰盒 Demo / 网页后台 / 系统替我推理”，哪里必须返工？

# 结语：当前唯一开发方向

《游园惊梦》现在不是要继续“堆更多功能”，而是把已经验证有价值的技术、剧情、模型和玩法真正合成一款统一的游戏：

真实可相信的听雨轩
↓
玩家形成空间记忆
↓
认知差异真正改变空间
↓
Borrowed View / Borrow / Anchor 让异常成为工具
↓
玩家通过行动得到案件事实
↓
旧证据不断获得新解释
↓
第五人 = 玩家
↓
删除 = 保护
↓
雨夜事故与延误救治
↓
第五种听雨轩
↓
事实清楚，解释开放

这条链路是后续剧情、关卡、美术、建模、程序、UI、音频和测试共同服务的唯一主轴。
